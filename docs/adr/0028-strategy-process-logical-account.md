# ADR 0028: 策略进程单逻辑账户 + N 挂靠账户

## Status

Accepted（2026-10-27 评审通过；2026-10-21 重写：原「策略进程单账户模型」由本版取代；同日设计评审确定「逻辑账户 + 挂靠账户」为最终模型，单账户只是阶段性简化）

## Context

- 目标用户从交易开拓者（TB）迁移：TB 的图表交易系统让策略面对一个**虚拟账户**——持仓由信号推算、与真实账户无关，`Portfolio_*` 等函数读的都是它；真实账户通过头寸管理器按「系统倍数」挂靠到策略单元，实盘与系统的差异由账户级头寸监控 + 手工「一键同步」对账（TB 没有基于策略的一键同步，因为账户持仓无法区分策略归属）。
- [ADR 0027](0027-bar-strategy-framework.md) 初稿按「单进程多账户（账户 = 实例维度）」设计；本 ADR 上一版为缩小 v1 范围改为「一个进程一个账户、框架不建模账户与规模」。用户确认后者只是阶段性简化，**最终目标就是 TB 式的「逻辑账户 + N 个按比率挂靠的实体账户」**，且多账户必须在同一策略进程内（「一个策略一个进程」是既有架构不变量）。
- 平台既有事实：策略身份 = 可执行文件名；订单帧 `DzOrderReq` 自带 `account_id`，td 按归属过滤，因此一个策略进程给多个账户发单不需要改帧结构；`DZ_FRAME_SET_LOGICAL_POSITION` 本来就按 `(strategy_id, account_id, instrument_id)` 上报，天然可按账户表达逻辑持仓。
- 账户的登录、凭据、交易接口归属完全属于平台（td 配置）；策略侧只持有账户标识与挂靠比率。
- 委托的 `position_effect` 以 `DZ_POSITION_EFFECT_AUTO` 为主（开/平/锁仓由 td 按账户配置解析，平台专项见 issue #82）；执行与记账的详细口径见 [ADR 0030](0030-attached-account-scaling.md)。

## Decision

1. **一个策略进程 = 一个策略 = 一个逻辑账户**：逻辑账户是纯虚拟的记账身份，不存在于 td 配置、不能登录、不参与订单路由；它只承载「策略自己的净持仓」这一本账（口径见 [ADR 0030](0030-attached-account-scaling.md)）。
2. **实体账户 0..N 个，动态挂靠**：每个挂靠账户有一个挂靠比率（`scale`）；策略逻辑看不见任何实体账户，也没有账户身份 API。0 个账户时策略照常运行（只记逻辑台账、不发实盘单）。
3. **账户生命周期在运行期由 UI 命令管理**：`account add <id> <scale>` / `account set <id> scale <v>` / `account del <id>` / `account list`；增删改命令带可选 `[sync|nosync]`（默认 `nosync`）与同步单价格选项 `[market]`（默认对手价）；命令成功后原子写回策略配置，重启后保留。
4. **同步只发生在增删改命令上**：`sync` = 按命令引起的逻辑持仓变化量先发差额单（add/set 补差、删除平掉），随后无论成交与否逻辑持仓立即按命令生效；`nosync` = 只改挂靠关系/比率、不发单。不查询账户实际持仓、不建成交台账、不提供独立的同步命令。
5. **删除账户立即移除**：逻辑上立即消失并上报清零，不等实盘成交；`sync` 时先发平仓单，平不掉的部分不再归框架管理。不判断逻辑持仓；`sync` 只发单、不确认成交。删除品种同样支持 `[sync|nosync] [market]`（见 ADR 0027 决策 13）。
6. **一键同步是平台/WebUI 的账户级能力**（未来实现）：比较账户实际净头寸与系统逻辑持仓、由操作员手工发起；策略框架只负责维护并上报逻辑持仓，不实现对账。
7. **净头寸口径**：系统只按净额记账与对账；账户内部多空明细、锁仓与今昨拆分不影响系统（由 td 按 AUTO 解析），失真可接受。
8. **AUTO 是 BarStrategy 唯一的委托 effect**：策略只表达买卖方向与手数；显式 `OPEN`/`CLOSE_TODAY` 等标准开平指令留给平台标准下单接口，供特定策略/品种、算法交易与 DIY 使用，BarStrategy 不建模。AUTO 的平台实现（接线 `OffsetConverter` 等）是本框架实盘联调的硬前置（issue #82，实现时需新 ADR supersede [ADR 0008](0008-td-position-model.md) 决策 5）。
9. **逻辑持仓的恢复靠历史回放**：进程启动时回放历史数据，B 照常下单但只做虚拟成交，回放完成即恢复逻辑持仓（依赖归档域；v1 归档未实现时冷启动、逻辑持仓为 0）。策略启动后即认为持仓正常；实盘是否匹配由操作员用一键同步负责。

## Alternatives

- **单进程多账户（ADR 0027 初稿，账户 = 实例维度）**：账户级实例集合、账户间数据隔离、迟到账户回放与视图拼接、账户 CRUD 全部进框架，策略还要处理账户维度；本 ADR 的「逻辑账户 + 挂靠」用一个放大后的虚拟台账满足同样需求，复杂度低得多。否决。
- **单账户多进程（本 ADR 上一版）**：N 个账户 = N 份 exe 与配置，部署与参数漂移靠模板/脚本，动态挂靠、统一逻辑持仓与 UI 视图都做不到；只能作为 v1 阶段性简化，不能作为终态。否决为终态。
- **物理主账户 + 挂靠**：把某个实体账户（scale=1）的成交当作逻辑持仓来源。主账户被移除/故障/换绑后逻辑身份丢失，逻辑持仓还会被单账户的拒单与部分成交污染；TB 的虚拟账户本来就不依附任何实体账户。否决。
- **框架内实现一键同步/对账**：需要平台真实持仓、跨策略归属与手工仓概念，天然是账户级能力；放进策略框架会让框架依赖 td 状态、破坏「逻辑归策略、实际归平台」的边界。否决（留给平台/WebUI）。
- **attach/detach 走配置文件 + 重启生效**：不满足「动态增删改」；每次调整账户都重启策略，丢掉回放续仓能力。否决。
- **框架内建模账户级数据隔离/每账户一套回放**：策略看不见账户，多账户只是同一逻辑持仓的不同比例镜像，没有独立时间线；纯增复杂度。否决。

## Consequences

- **策略 API 面**：`ctx.account_id()` 移除（逻辑账户没有独立 id 可暴露）；B 只见逻辑持仓、参数与行情；四个交易方法保留（TB/MC 名字；开平意图与 `volume=0` 规则见 [ADR 0027](0027-bar-strategy-framework.md) 决策 9，订单 effect 统一 AUTO），执行口径见 [ADR 0030](0030-attached-account-scaling.md)。命令 payload 为字符串（`UI_INPUT`/`OUTPUT_UI`），框架侧实现解析与字符串结果；dzweb 入口/权限/请求关联归 #6/#9。删除账户/品种不判断逻辑持仓、不撤单、不等待成交，残留由操作员处理。
- **配置**：新增 `accounts`（账户标识 + scale 列表）、`max_scale`（启动加载一次、盘中不可变）、取整策略等字段；删除 `account_id`（详见组件文档 §7）。命令改动原子写回配置。
- **上报**：`DZ_FRAME_SET_LOGICAL_POSITION` 改为按挂靠账户上报逻辑持仓，删除账户用「账户 + 空品种」通配清零；策略级虚拟持仓不单独上报。帧结构不变。
- **运维**：实盘与逻辑的匹配是操作员责任（一键同步，WebUI 未开发）；策略启动后不做持仓校验；重启后逻辑持仓依赖归档域回放（v1 冷启动为 0）。
- **故障域**：仍是一个策略进程一个故障域；一个进程挂多个账户后，进程故障影响全部挂靠账户（TB 同样），换来的是同一份逻辑持仓与统一对账视图。
- **性能**：下单路径多一层 N 账户循环与 N 条上报帧（N 通常 1–3，均在下单/命令的冷路径）；tick 热路径不变。
- **平台依赖**：委托 effect AUTO 需要平台专项（issue #82），实现前不能联调实盘下单；账户模式（净头寸/锁单/正常）由 td 解析，框架不限制挂靠账户模式，净额口径下多空明细失真可接受。
