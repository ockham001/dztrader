# ADR 0045: 交易账户身份、快照生命周期与准确性边界

## Status

Accepted（2026-11-03，交易数据架构调整）

## Context

- [ADR 0041](0041-sqlite-only-trade-store-schema-v1.md) 把四类交易记录改为"按交易日累积"的快照 / 流水表，但登录、重连、删除账户后重加、盘中切换柜台、其他终端交易等时序边界没有定义：旧快照会不会显示成当前持仓、重放会不会重复入库、锚点日会不会与持仓不一致，需要统一规则。
- `account_id` 由配置给出，平台内全局唯一是上层共识：下单请求帧按 `account_id` 路由（两个网关同时配置同一账户会重复下单），策略与 UI 按 `account_id` 识别账户，`seq` 水位按账户维护。`gateway_name` 是 td 进程实例名，运行期可变（改名 / 换实例），不能作为账户身份。
- 持仓 / 资金是绝对态：只有柜台查询是权威；本系统成交回报只能在内存增量维护，其他终端 / 其他软件的交易看不到逐笔。

## Decision

1. **账户身份**：`account_id` 全局唯一——同一时刻一个账户只属于一个交易接口实例。`gateway` 只作写入来源列（[ADR 0041](0041-sqlite-only-trade-store-schema-v1.md) 决策 3），不参与业务唯一键、不参与查询过滤。**配置入口校验**：UI 添加账户时拒绝与任何已知 td 配置重复的 `account_id`；**dzweb 是权威校验点**——按网关维护已知 td 配置（来自 `td-config` 帧），并把 `account_id → gateway` 注册表持久化到 `platform.db`（`market_sources` 同款小表），使 dzweb 重启、网关停机期间仍能校验；已禁用 / 离线账户同样占位。注册表**内存优先、`platform.db` 只是尽力而为的镜像**：配置帧到达时按网关整组 reconcile（以帧为权威，自愈错误状态）；DB 写失败只记 ERROR、不阻塞账户操作；启动加载失败则从空开始、随各网关配置帧重建；网关被移除时清掉该网关条目。内部错误最多让校验暂时少覆盖一个网关（已知降级），不得制造新的不一致或阻塞操作。td 侧配置内查重是既有行为，不是跨网关防线。**不做**跨进程锁 / 中心账户注册表 / master 协调（添加账户不经过 master，收益不值成本）。手工修改配置文件、或从未被 dzweb 感知的网关配置可绕过校验——属用户自担风险，在 `td-config` 契约写明。
2. **快照写入两条路径**（持仓 / 资金）：(a) 登录 / 重连后的**首个完整成功查询**（`is_last` 且无错）→ 单事务"删除该账户当日行 + 写入查询快照"（整组原子替换）；已就绪后的周期查询仅在有差异 / 消失时整组重建；(b) **日内增量**（本系统成交、活动挂单冻结、日切推导）→ 单行 upsert（含 `volume=0`）。查询失败不改表；建仓 / 平仓帧照常推送，库由下一次成功查询收敛。
3. **登录不清零、不预置 0**：首个完整成功查询之前保留上一次已知快照（含跨会话、账户删除后重加、盘中换柜台）。理由：`volume=0` 是"空仓"断言，隔夜有仓时它是错的，比"带日期的旧快照"更危险；原子替换保证读者只会看到旧快照或新快照，没有中间态。若 UI 需要表达"尚未同步"，用行内 `date` + 账户状态表达，不写假数据。
4. **锚点日一致性**：资金行只允许在持仓查询成功之后写入（登录收尾链顺序：持仓 → 资金；失败补查链同序）——td 侧由 `on_rsp_qry_trading_account` 的 `position_query_ok_` 守卫强制，持仓查询失败时不写资金行、不推资金帧；因此锚点日推进到当日时持仓行集已一致。不设"日切强制写资金行"特例——日切即重新登录，查询链本身会写当日行，预写反而制造资金有、持仓缺的不一致。（锚点日**取值表集合**的定义原在 [ADR 0041](0041-sqlite-only-trade-store-schema-v1.md) 决策 2 与 [ADR 0044](0044-strategy-sdk-db-layer-privatized.md) 决策 2，已由 [ADR 0046](0046-anchor-day-from-snapshot-tables-only.md) 修正为「`positions` + `trading_accounts` 两张快照表」；本决策的顺序约束不变，且正是 ADR 0046 成立的前提。）
5. **删除账户不删数据**：删除只推 Offline、销毁会话，四表行保留。重加或盘中换柜台后：**每次登录成功（含盘中重连）重新装载当日订单 / 成交基准**（`order_ref` / OrderSysID 匹配既有 `order_id`，`(exchange_id, trade_id)` 集合去重；装载在首条重放处理前完成；不做增量水位装载，登录频率低、当日行量级小），首个成功查询整组替换当日持仓、upsert 资金，`seq` 从 DB `MAX` 续号。历史交易日行不可变。td 内存只保留**当日**：订单最新态、成交去重键与每单成交累计（均价重建）、OrderRef 映射、当前持仓 / 资金；历史委托与成交只在 `trade.db`，不装载（现状 `td_prescan` 的全史装载在本轮删除）。
6. **准确性边界**：持仓 / 资金是"最近一次成功查询的截面"，不是逐笔实时；资金本轮不做周期查询（`qry_account_interval_s` 保留但未接入），资金行只在登录 / 失败补查链更新，盘中资金停在最近一次查询（已知限制；后续接入周期查询时必须保持"持仓成功后再写资金"的顺序）。其他终端交易：持仓由周期查询收敛（≤ `qry_position_interval_s`）；委托 / 成交只入库柜台回报给本会话的数据（实时流 + 登录重放），非本会话外部单可能晚到（下次登录）或缺失——记为已知限制，后续可用 `ReqQryOrder` / `ReqQryTrade` 周期补偿或对账（本轮不做）。
7. **收敛窗**：跨进程写同一交易库，旧会话已入队未提交的 persist 任务可能晚于新会话的整组替换落地 → 当日持仓短暂回到旧值，由下一次周期查询收敛（≤ 持仓查询间隔）；不丢行、不产生键冲突。不做跨进程取消 / flush 屏障（复杂度不值），在契约里写明该有界窗口。

**为什么不在唯一键里加 `gateway`**：加 gateway 会把账户身份拆成运行期实例维度——网关改名 / 换实例即分裂身份（而改名是契约允许的操作），且读路径仍是 `account_id` 作用域，键按 gateway 分区只会让同一账户的数据出现两套、查询语义错位；同 `account_id` 并行登录在帧路由层已不可用（重复下单），应检测而非存储。**为什么不把交易所单号（FrontID + SessionID + OrderRef、OrderSysID）当键**：会话三元组是登录会话域、跨会话不保证唯一；`OrderSysID` 交易所确认后才出现、本地拒单永远没有；用它做键只会引入第二种冲突源。二者都只作为 `ext` 引用，身份永远是 `order_id`（[ADR 0041](0041-sqlite-only-trade-store-schema-v1.md) 决策 6）。

## Consequences

- 正面：登录 / 重连 / 删除重加 / 换柜台 / 隔夜都有确定行为；不会出现"预置 0 假空仓"或旧会话覆盖新快照；重放不会重复入库；锚点日与持仓天然一致。
- 负面 / 已知限制：持仓精度的收敛受查询间隔约束，资金本轮无周期查询（盘中停留在登录 / 补查时刻的值）；跨进程残留写入有 ≤1 查询周期的收敛窗；其他终端的外部委托 / 成交可能晚到或缺失；同一 `account_id` 被用于不同真实账户时历史会混（配置语义问题，应用新 id，检测只能发现并行使用）。
- 契约：`td-data-sync`（登录日装载、重建 / 零帧、准确性表述）、`account-status` / `td-status`（字段名 `date`）、`rest` / `webui-ws`（`date`、锚点日语义）同步更新（[ADR 0041](0041-sqlite-only-trade-store-schema-v1.md) 决策 4）。
