# ADR 0061: 通知去重冷却默认值 5 分钟 → 10 分钟

## Status

Accepted（2026-11-28，来自 #530 复审；**部分取代** ADR 0060 决策 4 的冷却默认值，折叠语义不变）

## Context

ADR 0060 决策 4 定下两条默认值：同一指纹 **60 秒窗口**内合并计数、**5 分钟冷却**后才允许作为新条目重新出现。与此同时 ADR 0042 §4（与契约 `td-data-sync` §4）要求持久化持续故障的通知**每 5 分钟最多一次**，`td_persist_writer` 的 `sustained_notify_interval` 默认值因此也是 5 分钟。

两个默认值相等产生确定性缺陷：持续故障每 5 分钟重申一次，而 dzweb 的冷却判定是 `age >= cooldown`（`notify_cache.h`）——每条通知的间隔恰好等于冷却，永远被判成**新条目**而不是折叠。后果：

- `count` 永远为 1，「持续故障用计数折叠表达」（ADR 0060 决策 2/5）不成立；
- 同一故障每 5 分钟占用一条环形缓存，最终把 100 条缓存刷满、挤掉其它通知；
- REST 基线（逐条缓存）出现 N 行重复，实时视图与基线不同形。

这是**参数默认值**的冲突，不是折叠语义的冲突：折叠语义（唯一漏斗在 dzweb、指纹归一化、冷却后才重现、前端只在 `count>1` 时就地更新）保持不变。

## Decision

`webui.json` 的 `notify.dedup_cooldown_sec` 默认值从 **300 改为 600（10 分钟）**；窗口保持 60 秒，`td_persist_writer` 的持续通知间隔保持 5 分钟（ADR 0042 §4 不变）。

理由：只要**冷却 > 持续通知间隔**，每次重申都会命中折叠并更新该条目的最后发生时间，`count` 单调累加；10 分钟给 5 分钟间隔留一倍余量，避免时钟抖动/转发延迟落到边界。冷却仍是可配项，需要更快重现某个事件的部署可以调低——但必须保持大于产生侧的通知间隔。

**为什么不用其他方案**：

- **把持续通知间隔调到 < 5 分钟**：违反 ADR 0042 §4 与契约 `td-data-sync` §4 的「每 5 分钟最多一次」。
- **把冷却判定改成 `>`（严格大于）**：通知间隔由 `steady_clock` 驱动、进入 dzweb 时换算成 Unix 秒，抖动会让 `age` 落在 300 或 301 秒，边界解不稳定。
- **折叠时无视冷却（一旦折叠过就永久折叠）**：会把「故障恢复后再次发生」也吞进旧条目，重新引入 ADR 0060 明确否决的「彻底静默」。

## Consequences

- 同一指纹的可行动事件在 10 分钟内只保留一条记录（`count` 累加、时间戳更新），超过 10 分钟才成为新条目并重新提示。
- 契约 `notify-ui` 补一句默认值与「冷却必须大于持续通知间隔」的约束；`config.h` / 生成默认配置同步为 600。
- 已存在的 `webui.json` 若显式写了 `dedup_cooldown_sec: 300`，仍按用户配置运行（默认值只影响未配置项）；升级说明保留在 #530 的 PR 描述。
- 本 ADR 只改默认数值，不改变 ADR 0060 的折叠位置/指纹/广播形状/前端义务等决策。
