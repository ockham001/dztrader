# ADR 0050: dzweb 统计取消周期对账——`order_id` 单调水位判据

## Status

Accepted（2026-11-21，#410 / #416）

Supersedes（精确到句；未列出的决策与句子全部保留）：

- [ADR 0043](0043-dzweb-direct-db-query-and-ws-push.md) 决策 4 中「启动 / Ready / 日切从 DB 重算**并定时对账**」的「**并定时对账**」——废止；同句的重算触发保留（本 ADR 另补「在线集合变化」触发，与现状实现一致）。该决策主体「dzweb 内存计数器维护 4 个值」**保留**，但「首见判据」由活动表推断改为每账户 `order_id` 单调水位。

契约同步：《帧契约：REST API》§2.9.5（删周期对账、写水位判据、删「已知精度边界（成交均价刷新帧）」段）；《帧契约：TD 数据同步》§8 统计计数器与实现注记；`docs/components/dzweb.md` 统计计数器节。ADR 0043 正文不改，只在 Status 段加引用注记。代码侧删除与实现见 #416。

## Context

dzweb 的 4 个统计计数器（总 / 未成交 × 笔 / 手）采用「增量维护 + 30s 周期对账」：周期对账用 `SELECT COUNT(*)` 等聚合覆盖内存值，抹掉增量累积的偏差。它存在的理由是一个**真实的计算错误**：

`TdStatsCounter` 判断一条 `ORDER_REPORT` 是否首见的依据是「`order_id` 在不在活动（未成交）委托表」。这个判据的前提被写进了头文件注释：「终态委托不会再收到 `ORDER_REPORT`」。**前提是错的**：td 在每笔成交使成交均价变化时，会以**新 `seq`** 刷新该委托行并再推一帧，对象包括已 `AllTraded` / `Cancelled` 的终态委托（《帧契约：TD 数据同步》§3，`refresh_order_avg`）。终态委托此时已不在活动表，于是均价刷新帧被当成新委托：`total_orders` +1、`total_volume` 再加一遍 volume；30s 后的周期对账再把 2 改回 1。

**这是用定时器纠正方法错误。** 正确做法是修判据——让「首见」不依赖「终态后不再有帧」这个错误前提。

`order_id` 具备判定首见所需的性质（已从代码核实）：

1. `OrderIdMeta::generate()` = `fetch_add(1)`，全平台共享同一个计数器（`CHANNEL_NAME_ORDER_ID`），单调不回退；
2. master 启动时按交易库 `MAX(order_id)+1` 播种，`ensure_at_least` 是 CAS fetch-max（幂等、单调）；
3. 同一委托的后续帧必然复用**同一个** `order_id`（本地单复用 `TD_ORDER_REQ` 携带的号，外部单复用首次分配后映射的号），因此「见过的委托」的帧永远 ≤ 水位。

判据还需一个**常态前提**：新委托首帧的到达顺序与 `order_id` 分配顺序一致。该前提对外部单成立（在 `on_rtn_order` 里取号、帧同时产生）；对本地单只是**常态成立**而非严格保证——本地单的 `order_id` 由策略进程在下单时分配（`dz_place_order`），首帧却要等 td 收到柜台回报时才产生（本地单复用 `req.order_id`，`place_order` 本身不推 `ORDER_REPORT`）。多策略跨进程共挂同一账户（ADR 0030）或本地单与外部单并发时，低号单的首帧可能晚于高号单——见 Consequences 的已知边界。

因此每账户一个 int64 就够：内存 O(1)/账户（比活动表还小），符合 ADR 0043 决策 1 的「有界」原则。

## Decision

1. **首见判据 = 每账户 `order_id` 单调水位**（max_order_id，一个 int64）：
   - `order_id > max_order_id` ⇒ 真新委托：`max_order_id = order_id`，`total_orders += 1`、`total_volume += volume`；
   - 否则 ⇒ 见过的委托（状态迁移 / 成交均价刷新帧）：只按活动（未成交）委托表调整未成交口径，`total_orders` / `total_volume` 不动。不在活动表的已知委托（终态均价刷新帧）没有未成交口径贡献，忽略。
2. **取消周期对账**：删除 `kTdStatsReconcileIntervalSec`、`TdDomainService::set_reconcile_scheduler` 与 `main.cpp` 的 `runEvery` 注册。统计不再有任何「定时纠正」路径。
3. **保留全量重算触发点**：启动 / 账户 Ready（**无条件**）/ 在线集合变化 / 日切。它们不是「定期纠正」，而是必要的一致性锚点——同时负责两条水位的**初始化**：
   - `seq` 重放水位（四表 `MAX(seq)`）：只由重算写入、增量永不推进，帧 `seq ≤ 水位` 跳过（登录「重推最后一条」用原 seq 的去重靠它）；
   - `order_id` 水位（orders 表 `MAX(order_id)`）：重算从 DB 建立、真新委托帧推进。
   - **两条水位的初始值只能来自交易库**：`seq` 水位只由重算写入；`order_id` 水位由重算用 `MAX(order_id)` **覆盖**——不能用内存最大值代替，否则 DB 快照没纳入的未落库委托会在重算后被判成「已见过」而永久丢计。增量只在初始值之上推进（账户无该条目时从 0 起，只对真新委托推进）。重算的 `MAX(order_id)` 与既有 `MAX(seq)` 同一条 GROUP BY 查询（orders 表），不增加查询次数。
4. **契约**：`rest` §2.9.5 删周期对账、写水位判据、删「已知精度边界（成交均价刷新帧）」段——该精度边界不再存在。

**为什么不用其他方案**：

- **(A) 保留 30s 周期对账**：正是要拿掉的东西。用户要求明确——「计算对了就是对了，不需要对账；计算错了是方法有问题，应该修方法」。定时器只是在错误持续期间卖出一个固定延迟；取消后统计数字只在真实业务变化时跳变。
- **(B) 为终态委托保留一个 `order_id` 去重集合**：无界。终态委托集合随时长单调增长，与 ADR 0043 决策 1 的「有界」原则冲突；`order_id` 水位是同一判据的 O(1) 压缩。
- **(C) 增量推进 `seq` 水位来判重**：错。契约 td-data-sync §2 第 4 条明确「跳过判断只准用 DB 查得的 `seq` 水位」；增量推进会让水位超过 DB，重算后「已计入但未落库」的帧既拿不到、水位又已越过，永久丢帧。
- **(D) 用「活动表 + 终态表」两表推断**：仍是按状态集合推断首见，会漏掉「刷新帧在终态之后到达」的一整类未来帧形态；水位判据只依赖 `order_id` 的单调分配与首帧顺序的常态前提，与帧形态解耦。

## Consequences

**正面**：统计不再靠定时器纠正——`total_orders` / `total_volume` 只在真实新委托时增长，成交均价刷新帧不再多计；少一个周期任务与一条 `runEvery` 注册路径（`main.cpp` 的启动窗口约束、IO 线程串行注册与之同去）；判据从「活动表的隐式前提」变成一条显式不变量（`order_id` 单调分配），更易推理。

**负面 / 已知限制**：

- **首帧倒序窗口（已知少计边界）**：上述常态前提不成立时——低号新单的首帧晚于某个高号单的首帧——该低号单会被判成「已见过」而少计（`total_orders` / `total_volume` 各少 1 次），并保持到下一次全量重算（启动 / Ready / 在线集合变化 / 日切）从交易库重建计数器。触发条件是多策略跨进程共挂同一账户（ADR 0030）或本地单与外部单并发导致首帧顺序与取号顺序倒置；窗口窄但**不是不可达**。这是消除「终态均价刷新帧必然多计」的取舍：旧口径每笔均价刷新都会多计（盘中反复发生），倒序窗口只在上述并发下偶发。
- **判据依赖 `order_id` 的单调分配**：若将来引入会复用 / 回排 `order_id` 的入口（例如跨机导入历史订单、按账户分段分配），水位判据会把低号新委托误判成「已见过」。ADR 0041 决策 2 的 `orders` 键带 `date` 正是为「计数器异常 / 跨机导入造成的跨天同号」做容错——那种异常数据下统计会少计，属异常路径。新增取号入口必须保持「全局单调」。
- **异步持久化窗口不变**：帧先于库提交到达时计数器可能短暂领先已提交数据，持久化追上后一致；不再有定时对账把它「抹平」，但它本来也不是错误。
- **重算仍是重同步点**：td 崩溃重启后 `Ready` 无条件重算、日切重算等触发点保留；职责是重建水位与口径，不是纠正误差。

**契约影响**：《帧契约：REST API》§2.9.5；《帧契约：TD 数据同步》§8 与实现注记；`docs/components/dzweb.md` 统计计数器节。代码侧删除与实现见 #416。
