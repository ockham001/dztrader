# ADR 0010: 帧号按接收域重新分配 + 帧值单一真相源

## Status

Accepted

## Context

项目初期帧号是"历史增量"式分配（系统帧 10-25、UI/进程 101-121、行情 1000-1016、
交易 2000-2118、策略 3001-3003），期间大量帧被删除/替换，留下空洞与死号；
同时接收方 `switch (frame_type)` 的分派成本与"热帧跨几个值簇"相关。

两条独立动议合并处理：

1. **提速**：把同一接收域（同一进程）的帧挤进**尽量少的连续值簇**，使 `switch` 生成
   单张跳转表，逐帧成本固定为"一次段判定 + 一次间接跳转"。
2. **可维护性**：帧值此前散落在契约、注释、日志、测试断言里（约 115 处），
   违反单一真相源，删/改帧号时无人能保证同步。

约束（用户明确）：初期项目**不需要考虑兼容性**，帧值可整体重排；但**帧名是唯一引用方式**。

## Decision

### 1. 帧号按接收域分段，段内稠密，只追加不插空

| 值域 | 归属 |
|---|---|---|
| 0-31 | 填充、SHM 通道维护与预加载、日志、UI 通知、快照、进程控制/状态/配置、自动登录、进度、关闭 |
| 32-63 | 逻辑持仓、策略上行输出 |
| 64-95 | 行情数据与控制 |
| 1000-1023 | 行情源生命周期通知 + 交易推送（委托/成交/持仓/资金/合约/费率/结算/账户状态） |
| 1024-1123 | 交易控制/状态/账户与费率查询/风控拒绝/出入金改密 |
| 2000-2099 | 策略输入输出与本地调度 |

新帧取同段内下一个空闲号并追加在段尾；禁止插空档、禁止跨段散布同一接收域。
契约《帧契约：通用规则》§3 记录该规则，分段表写在 `data_type.h` 的注释里。

### 2. 帧值的唯一书写位置：两个头文件

- `libs/strategy_api/include/dztrader/data_type.h`（策略可见帧）
- `libs/core/include/dztrader/core/core_data_type.h`（平台帧）

帧值以 `#define DZ_FRAME_X ((DzFrameType)值)` 的形式各写一次（描述写在该行上方的
注释里）；契约、注释、日志、测试一律引用 `DZ_FRAME_*` 帧名，**禁止写值**。

> 2026-09 修订：中间版本曾以两张 `.def` X-macro 登记表为真相源，目标相同但多了一层
> 间接（展开点、段断言表、只为该表服务的查重测试），已删除，回落到两个头文件直接定义。

### 3. 无写端且无读端的帧不保留号

删除该行定义，号留给后续新帧（与旧"帧号保留不复用"约定相反）。本次删除：
`DZ_FRAME_TD_SUBSCRIBE`、`DZ_FRAME_TD_NOTIFY_UI`、`DZ_FRAME_TD_QUERY_ALL`
（三者除测试断言外无任何写端/读端）。
`DZ_FRAME_TD_POSITION_DETAIL` 一度因 SDK 透传白名单仍引用而保留；后续核查该白名单条目亦为死代码
（无写端、无 payload（无 `DzPositionDetail`）、无回调，CTP 侧持仓明细查询已 retired），2026-09 一并删除，帧号 1013 释放。

2026-09 复核再删一帧：`DZ_FRAME_TD_SETTLEMENT_INFO` 同样无写端（td 侧只有 CTP 结算确认握手，
既不产帧也不查结算单文本）、无 payload、无回调，仅存于 SDK 透传白名单；删除后帧号 1009 释放。

2026-09 复核再删一帧：`DZ_FRAME_TD_ERROR_REPORT` 从未有过写端（`git log -S` 查全历史只有测试断言，
无任何 `write_*` 调用）、无 payload 类型、无契约、无回调。CTP 下单报错已由 td 转成
`status=DZ_ORDER_REJECTED` 且 `remark` 带错误文本的 `ORDER_REPORT`（本地风控拒单同路径）送达策略，
不存在信息缺口；删除后帧号 1008 释放。

### 4. 契约面由测试锁定（`apps/ctp/tests/frame_types_test.cpp`）

测试只写帧名不写值：策略可见帧清单、策略热路径连号。
原"帧值断言表"与表驱动的全量查重测试随登记表一并删除。

## Alternatives

- **保留旧帧号，只在接收方做分派优化**：实测连续帧号收益 < 2 ns/帧（见附录），
  但值仍散落在 ~115 处、死号仍占位，可维护性问题不解决。**否决**（本项目无兼容包袱）。
- **引入值翻译层（LUT/compact id）**：实测劣化 1.7-1.8 倍（每帧多一次查表）。**否决**。
- **帧头加"分派索引"字段**：ABI 变更 + 所有写端承担计算，收益同样 < 2 ns/帧。**否决**。
- **帧号保留不复用**：初期阶段死号占位与"段内稠密"直接冲突，且无外部消费者。**否决**。

## Consequences

- **协议 ABI 破坏性变更**：全部进程需同版本升级；共享内存通道文件（`.dztrader_dev` 下）
  与旧版本不兼容，测试/调试前清空 SHM 目录即可。
- 接收方 `switch` 的分派簇数下降：策略 SDK `handle_event` 的 case 全部落进
  交易推送段（1000-1023）单簇；`dispatch_frame` 由 3 簇降为 2 簇。
- 新增帧的流程固定为"对应头文件加一行 `#define` + 契约写帧名（不写值）"；
  段归属按 `data_type.h` 的分段表人工核对。
- 历史归档（`docs/specs|plans|superpowers/**`）保留旧帧号，不修改、不作为真相源。

## 附录：为什么"值连续"本身只值 < 2 ns/帧（实测）

GCC 15 `-O2` 对散列帧号并非生成比较树，而是**按值簇分段、每簇一张跳转表**：
`dispatch_frame` 的旧值集合生成 3 张表 + 每簇一次区间判定。实测（同 case 集合、
仅改值分布，处理体独立不内联）：

| 输入分布 | 散列帧号 | 连续帧号 |
|---|---|---|
| TD 回报主导 | 18.6-19.4 ns/帧 | 14.5 ns/帧 |
| 均匀分布（17 帧等概率） | 13.4-13.7 ns/帧 | 13.2-13.5 ns/帧 |
| 单帧 99% 偏斜 | 7.5-7.7 ns/帧 | 5.9-6.5 ns/帧 |

仓库自带基线 `dz_shm_perf_bench`（写→唤醒→读往返）median 12400 ns，
TD 回报帧的处理体本身是微秒级——即**重排的收益不来自"值连续"，
而来自"把同一接收域的热帧并进同一段"**（簇数减少）。这也是本 ADR 把
"按接收域分段"写成硬规则、而不追求"全局连续编号"的原因。

## 修订

- 2026-09：删除 `DZ_FRAME_BAND_*` 段基址常量（6 个）。全仓生产代码零引用，只有两个测试拿它断言段归属，
  属于"没人用的维护层"。分段信息保留为 `data_type.h` 的注释表格；同时把交易推送段上界写实为 1000-1023，
  消除与交易控制段（1024-1123）的预留区重叠。
