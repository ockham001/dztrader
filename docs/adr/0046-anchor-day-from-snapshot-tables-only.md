# ADR 0046: 持仓 / 资金的账户锚点日取自两张快照表

## Status

Accepted（2026-11-05，#249 持仓垂直切片）

Supersedes [ADR 0045](0045-trading-account-identity-lifecycle-and-accuracy.md) 决策 4 末句与契约 rest §2.9.1 中「锚点日 = 该账户**四表** `MAX(date)`」的表述——只改锚点日的取值表集合，ADR 0045 的其余决策（登录不清零、整组原子替换、资金行在持仓成功后写入、历史行不可变）全部保留。

## Context

[ADR 0045](0045-trading-account-identity-lifecycle-and-accuracy.md) 决策 3 要求「登录不清零、不预置 0」：首个完整成功查询之前保留上一次已知快照，理由是 `volume=0` 是"空仓"断言，隔夜有仓时它比"带日期的旧快照"更危险。决策 4 同时把锚点日定义为该账户**四表** `MAX(date)`，用来说明"锚点推进到当日时持仓行集已一致"。

实现 #249 的持仓 REST 时这两条撞在一起：

- `orders` / `trades` 是**追加流**，登录重放与实时回报会先于持仓 / 资金查询落库（td 登录链：登录日装载 → CTP 重放 → 持仓查询 → 资金查询）。
- 于是登录当天只要有一笔委托或成交，四表口径的锚点就推进到当日；而持仓查询**失败**时 `positions` 当日无任何行。
- 结果：持仓列表按锚点日过滤 → 返回空数组，前端显示"空仓"。这恰是 ADR 0045 决策 3 判定为最危险的假断言，且让本票 AC「登录失败/查询失败保持上次已知快照」无法成立。

反过来的顾虑是「当日全平后不得显示昨日幽灵持仓」。检查该场景：平仓走整组原子替换（删该账户当日行 + 写查询快照），资金行又只在持仓查询成功后写入——两者同属快照表，锚点必然同步推进到当日，"当日持仓行集为空"就是真空仓。

## Decision

**账户锚点日 = 该账户 `positions` 与 `trading_accounts` 两张快照表的 `MAX(date)`**；`null` = 该账户两张表都无行（无任何成功查询过）。

- 不改两张快照表的写入路径：它们只在完整成功的柜台查询上写入（ADR 0045 决策 2/4），因此锚点日恒等于"最近一次成功查询所属交易日"，天然满足"查询失败保持旧快照"。
- 委托 / 成交追加流表**不参与**锚点日取值——它们不以日为单位代表账户截面，把它们算进锚点只会制造"快照缺项 + 锚点已推进"的窗口。
- 账户全集仍按契约 rest §2.9.1：在线账户 ∪ 注册表 ∪ **四表**中出现过的 `account_id`（这里是"该账户是否存在"的全集判定，与"取哪个日期的行"是两件事，故意保留四表以保证删户后历史数据仍可见）。

**为什么不是"有当日持仓行就用当日、否则回退到上一日"**（即按行自适应回退）：那样空仓（当日全平）与"查询失败"两种状态在数据上不可区分——两者都是"当日无行"，回退会把真空仓显示成昨日持仓（幽灵），不回退则把查询失败显示成空仓。用快照表锚点 + 行内 `date` 才能区分：空仓时锚点已是当日且行集为空；查询失败时锚点停在上一成功日。

## Consequences

- 正面：查询失败/登录失败期持仓与资金照常可见（带数据日期），不会出现假空仓；当日全平不会回退显示幽灵持仓；两个目标由"锚点取自快照表"这一条同时满足，不需要额外的回退规则。
- 负面 / 已知限制：锚点日推进依赖"资金行在持仓查询成功后写入"这一顺序（ADR 0045 决策 4）——若将来把资金查询改成独立的周期查询，必须保持该顺序，否则资金行单独把锚点推进到当日会重现本 ADR 要消除的窗口。
- 契约：rest §2.9.1 改为"两张快照表 `MAX(date)`"并写明理由；`td-data-sync` / `rest` 的锚点表述同步（[ADR 0041](0041-sqlite-only-trade-store-schema-v1.md) 决策 4 的表示层约定不变）。
