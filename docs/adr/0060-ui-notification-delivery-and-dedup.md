# ADR 0060: UI 通知的产生、分级与去重

## Status

Accepted（2026-11-27，用户当面拍板，承接 5 条 UI 反馈中的第 4、5 条）

Superseded-in-part：[ADR 0061](0061-notify-dedup-cooldown-default.md) 取代本 ADR 决策 4 的「5 分钟冷却」**默认数值**（改为 10 分钟，折叠语义不变）。本 ADR 决策 1/2/3/5/6 与决策 4 的其它内容继续有效。

契约同步：《帧契约：UI 通知》payload 追加可选 `count` 字段、「前端义务」改写（阻断式展示 → 常驻展示）；`GLOSSARY.md` 新增「消息中心」「即时提示」「常驻通知」「通知去重」，改写「UI 通知」词条。实现票：通知体系票（T3）。

## Context

`DZ_FRAME_NOTIFY_UI` 通道与前端分发链路**已存在但只接了一半**：

- 后端有 `NotifyUi` 发送器、dzweb 有 `NotifyDomainService`（写环形缓存 + WS 广播）与 `GET /api/notifications`；
- 前端 `useNotifyStore()` 收 `notify_ui` 后**只发 toast**，`items` 缓存 100 条却**没有任何渲染消费方**；
- 仪表盘右下角「消息」面板是**硬编码演示数据**（`DashboardView.vue:345-355`，标题挂「演示」标签）。

三个具体缺陷：

1. **`popup=true` 是阻断式展示**：`App.vue:116-138` 渲染全屏遮罩 + 居中卡片 + 「确认」按钮，`z-index:10000` 压住整个界面。它阻挡行情 / 持仓 / 委托，正是盯盘场景最不能接受的形态。7 个站点用它（交易连接超时 / 认证失败 / 登录失败 / 结算确认失败 / 合约加载失败 / 持仓基准查询失败 / 持久化 flush 超时）。
2. **同一事件在日志里出现两个级别**：`NotifyDomainService::on_notify_ui` 对每条进 UI 的通知补打一行日志，且 error 级别打成 `SPDLOG_WARN`（`notify_domain_service.h:40-44`）——于是同一事件日志里既有进程侧 ERROR 又有 dzweb 侧 WARN。`td_persist_writer` 另有「首次 ERROR → 持续期 WARN」（`:657` / `:665`）同一事件两级别。
3. **无去重、无限流**：`notify.ts:31-49` 逐条直发 toast。CTP 拒单（如「平今仓位不足」）是**高频且部分正常**的事件（策略试探、跨期套利都会触发），直连会刷屏。

同时确认了一个**能力缺口**：CTP 拒单路径（`on_rsp_order_insert` / `on_err_rtn_order_insert`）**完全没有 `notify_` 调用**，只写 `SPDLOG_ERROR`（`td_account_session.cpp:2729` / `:2827`）——用户看不到拒单原因，这正是「故意的平今仓位不足」没进消息中心的根因。

## Decision

1. **通知的产生是显式白名单，不从日志 sink 桥接。**
   全仓 `DZ_NOTIFY_*` 调用点 39 个，CTP 回报路径的 warn 是海量的（未知枚举、外部单重放、重放过滤器吞单）。把 spdlog warn/error 桥到通知总线会瞬间淹没消息中心，且「是否常驻」无法在日志行上表达。
   **白名单判据**：用户能感知、且能采取行动的事件。首批只含两类——**会话/连接类失败**（登录链各段失败、持仓基准查询失败、持久化故障与恢复）与**柜台拒单类**（下单被拒、撤单被拒）。**不接**：未知枚举告警、外部单重放告警、重放过滤器吞单、`place_order` 本地校验拒单（策略自己造成的，策略日志足够）、批量行情类。后续接入**从少到多**，每次只加一类。

2. **同一事件只有一个级别；级别不随呈现面变化。**
   禁止同一事件既发 WARN 又发 ERROR。持续故障用**计数折叠**表达（见决策 4），不靠降级成 WARN 来「弱化」。三个级别（info / warning / error）全部保留、消息中心照常显示原色——三种颜色是运维必需的信息，抹成一个级别会丢信息。

3. **阻断式遮罩弹窗删除，`popup` 语义改为「常驻」。**
   `popup=true` 从「打断用户（全屏遮罩 + 必须点确认）」改为「**不自动消失、可手动关闭、不遮挡**」的右下角常驻 toast。界面永不被挡，用户也不必点。
   理由：信息强度不必靠遮挡获取——账户卡片的失败态 + 消息中心留档已经给出同样的信息；而遮挡行情/持仓的代价远大于收益。契约「前端义务」随之从「必须打断用户展示」改写为「必须以常驻方式呈现直到用户确认或关闭」。
   连带删除：`App.vue` 的 `popup-overlay` / `popup-modal` 块与 CSS、`notify.ts` 的 `popupQueue` / `popupCurrent` / `ackPopup`、`AppNotifyPopup.spec.ts`。

4. **去重在 dzweb 折叠，不在前端。**
   `NotifyDomainService` 是唯一漏斗，在此合并：指纹 = `source + level + 归一化文本`（归一化 = 抠掉订单号 / 时间戳 / 价格等动态值）；同一指纹 **60 秒窗口**内合并并 `count++`、**不重复推送**（已在 UI 的那条原地更新计数）；窗口内重复**更新最后发生时间**（运维据此判断是否仍在持续）。同一指纹 **5 分钟冷却**后才允许作为新条目再次出现（避免持续故障刷屏，又不会彻底静默）。窗口与冷却进 `webui.json` 配置项。
   两种方案被否：(a) **前端折叠**——刷新后历史（来自 `GET /api/notifications`）是原始条目，折叠信息丢失，且后端环形缓存被同一噪声占满；(c) **产生侧各自去重**——分散在各进程，规则必然不一致。

5. **日志与通知的级别分工：一处最合适，转发不另立级别。**
   dzweb 的「已转发」日志降为 DEBUG（它是转发轨迹，不是独立事件，不该以 WARN 形态再报一次）；进程侧事件日志保留原级别。`td_persist_writer` 的持续故障不再降级成 WARN，改为 LEVEL 不变 + 折叠计数。

6. **消息中心是留档面，toast 是即时面。**
   两者是同一事件的两个呈现面，不是两个通道：消息中心全量可回溯、刷新后仍在（`GET /api/notifications` 拉历史 + WS `notify_ui` 增量）；toast 短暂（info 4s / warning 6s / error 10s，hover 暂停倒计时，最多同时 3 条，超出排队）。仪表盘面板显示最近 50 条，配「查看全部」抽屉（100 条 + 级别筛选）与顶栏未读徽标。

**为什么不用其他方案**：

- **(A) 保留阻断式遮罩、只做去重**：去重能降低频率但改不了性质——多账户同时登录失败时仍要点 N 次，且每次都挡住整个界面。频率降低不解决形态错误。
- **(B) 日志桥接兜底（warn/error 自动进消息中心）**：覆盖面看似完整，但 CTP 回报路径的 warn 数量级远大于有用信息，且重复（同一异常在多个 catch 层各打一次）。消息中心的价值取决于信噪比，兜底式桥接会把它变成第二个日志查看器。
- **(C) 消息中心只保留一个级别（统一叫「告警」）**：会丢掉「需不需要立刻处理」的区分——error 是「现在坏了」，warning 是「值得看一眼」。摘要是靠聚合与未读表达，不是靠抹平级别。
- **(D) 前端折叠去重**：见决策 4，历史与缓存两层都会失真。

## Consequences

- 契约 `notify-ui` 需追加可选 `count` 字段并改写前端义务——**契约先行，代码随后**。
- 仪表盘「消息」面板从演示数据切为真实数据后，`DashboardView.vue` 的「演示数据」横幅只剩「策略」一项（委托面板由 T2 接入），横幅文案需同步改写。
- 拒单进消息中心后，**用户会看到策略反复触发同一拒单**——靠去重折叠成一条 `×N` 控制噪音；若实际仍吵，说明白名单该收窄，而不是加更多去重规则。
- 遮罩弹窗删除后，`layout.css:45` 那段实测叠层注释（9000 banner / 9500 skip link / 9999 toast / 10000 遮罩）需改写：toast 成为最高层。
- 顺带发现但**不在本 ADR 范围**的两处历史遗留（只记录不处理）：`components.css:163-196` 的 `.ds-notif` 整套零消费方；`UserManagementView.vue:398` 的局部 toast 与全局 `ToastContainer` 是两套独立实现。
