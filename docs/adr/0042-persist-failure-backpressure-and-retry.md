# ADR 0042: 交易持久化的失败策略：不阻塞、不丢数据、退避重试

## Status

Accepted（2026-11-03）

## Context

- `PersistWriter` 现状：队列硬上限 10 万，满时 `enqueue` 阻塞调用线程；批事务失败整批丢弃；关停时直接丢弃未入队任务。
- DB 写入可能因磁盘满、锁等待、连接打开失败等持续失败。交易链路必须继续可用：持久化失败不能反压 SPI / 主线程、帧推送与 WebSocket 实时链路。

## Decision

1. 队列**不设硬上限、入队不阻塞**（调用方只做内存入队；积压由内存兜底并设阈值告警）。
2. **事务提交成功后才出队**；失败批保留在队首，writer 线程主动退避重试（1s → 2s → 5s → 10s → 30s 封顶），不依赖下一次业务事件触发。
3. `busy_timeout` 提升到 10s；打开失败按同一退避重开连接；任何失败都不丢数据。**打开 / 迁移失败被判定为文件损坏**（`SQLITE_CORRUPT` / `SQLITE_NOTADB` / 文件头非法）时：旧库改名保留（供排查）、新建空库、记 ERROR，交易继续（`trade.db` 不是交易真相源，真相在柜台与 td 内存态）；**不在同一坏文件上无限重试**。
4. 通知分级（只定义语义，UI 展示留给后续统一规划）：首次失败 ERROR 弹窗 1 次；持续失败每 5 分钟最多 1 次 WARN 弹窗；恢复 INFO 1 次；不新增持久化状态字段 / 常驻横幅。
5. 登录 flush 屏障 5s 超时后照常广播 Ready + ERROR 通知；持久化降级不得阻塞交易、帧推送与 WS。
6. 进程退出时排空失败则不落盘、记录 ERROR 后退出（按用户决定，登记为已知限制）。

**为什么不用"满了就阻塞 / 失败就丢"**：阻塞会让 DB 故障反压交易实时链路；丢弃会让数据静默缺失，违背"交易库是审计与回看依据"的定位。

## Consequences

- 内存占用随积压增长，需要阈值告警与人工抢救窗口；DB 修复后自动追平。
- 损坏重建后，历史查询缺口由备份 / 归档兜底（本轮不做实现，见 ADR 0041 决策 1 文件命名与备份路线）。
- 测试需覆盖：失败重试、恢复后追平、通知限频、flush 超时放行、关停路径。
- 契约：`td-data-sync` 中 Ready 与持久化的关系改为由独立错误通知表达。
