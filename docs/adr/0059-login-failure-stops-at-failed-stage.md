# ADR 0059: 登录链失败停在失败阶段（失败态 + `last_error` 分工）

## Status

Accepted（2026-11-26，#492 / spec #491）

部分取代 [ADR 0051](0051-gateway-session-control-vocabulary-and-ui.md) 决策 3 与 Consequences 各一句（精确范围见 Supersedes 段）；ADR 0051 的其余决策继续有效，正文不改，只在 Status 段加引用注记。

契约同步：《帧契约：进度推送》「网关会话进度骨架」改写为通用规则（失败停在失败阶段；回退只表示「会话尝试没停在链上任何一段就结束了」= 主动中止或前置连接超时；不含任何接口类型专有的失败态数值与码表）；`GLOSSARY.md` 新增「登录失败态」。各接口类型的失败态集合、`progress.current` 数值与 `last_error` 字段 / 码表由后续实现票在自己的契约里补——本 ADR 只定通用规则。「后续实现票」= #493（通知出口收敛，行为不变的预重构）与 #494–#497（四条失败路径 + md 对齐）。

## Context

诊断 #488 / #407 的结论：td 登录链的任一段失败**回退到前一段的正常状态**——

| 失败 | 从 | 回退到 | 用户看到 |
|---|---|---|---|
| 认证失败（`auth_code` 错） | 3/10 授权验证… | `Connected`（2） | 「已连接」 |
| 密码错误（登录被拒） | 5/10 用户登录… | `Authenticated`（4） | 「已授权」 |
| 结算单确认失败 | 7/10 结算单确认… | `LoggedIn`（6） | 「已登录」 |
| 合约加载失败 | 8/10 加载合约… | `LoggedIn`（6） | 「已登录」 |

两个后果：

1. **`state` 字段说谎**：明明是结算失败，报 `LoggedIn`；进度条倒退回前一段，读起来像正常流程的某一步。账户页展示的「已登录」与账户实际不可交易相互矛盾。
2. **失败不可持久回看**：`RTN_TD_STATUS` 没有 `last_error`，失败只经 `NOTIFY_UI` 弹窗一闪而过；前端事后无法回答「这账户为什么停住了」，登录 pending 只能等 45 s 兜底超时。

同时，前端清除登录 pending 的唯一可靠信号是 `progress.current` 回退——一旦失败改成「停住」，该信号消失，pending 会悬挂到兜底超时。所以「失败态」与「回退语义」是同一个决策的两面，必须一起改（#491 把 #489 与 #427 合并即为此）。

## Decision

1. **失败态表示「在哪一段失败」**：会话建立期内，链上每一个可失败的段在失败后**停在它自己那一段**——`progress.current` 取该段数值、不回退到上一段，`desc` 描述该段失败。失败态**不占端点**（既不是 `min` 也不是 `max`）。失败态的个数 = 链上可失败的段数，不是全平台统一值：td 的链有认证 / 登录 / 结算确认 / 合约加载四段，md 只有登录一段（故 md 只有一个失败态）。
2. **失败原因由 `last_error` 承载**：失败态只回答「哪一段」，段内具体原因（柜台拒绝 / 超时 / 解析失败 / 查询失败…）由该接口类型状态帧的 `last_error` 承载（机器码 + 可读消息 + 错误号 + 时间戳）。两者同一次状态转移写出、同一帧发布，缺一不可。
3. **`current` 回退的语义收窄为「会话尝试没有停在登录链的任何一段就结束了」**，只覆盖下面两类，二者都表示「这次尝试到此为止」：
   - **主动中止**：登出（→ `min`）、前置断线（回落到连接段）。
   - **登录链之前就没建立起来**：前置连接超时（从未连上 → `min`，见决策 7）。

   **登录链内部的失败一律停住、不回退**——这是本 ADR 与旧口径的分水岭：链内失败不再借用回退信号。

   > 与父 spec 措辞的偏差（有意）：#491 决策 2 把回退只说成「主动中止（登出 / 断线）」，但同一份 spec 的决策 5 又规定连接超时回 `Idle`——从 `1` 回到 `0` 本身就是一次回退，两条按字面读互相矛盾。本 ADR 以决策 5 的实际语义为准，把回退表述为上面两类，使两条决策同时成立。
4. **通用规则进《帧契约：进度推送》会话骨架，具体数值留在各接口类型契约**：骨架只写「建立期单调不减 / 失败停住 / 回退只覆盖上述两类 / 失败不占端点」；阶段数、失败态数值与失败码表由各接口类型契约定义，骨架不复述——两份文档各写一遍必然漂移。
5. **超时与柜台拒绝同等对待**：段内超时与柜台明确拒绝进同一失败态、写同一 `last_error`，靠 `code` 区分。用户不需要关心「柜台拒了」还是「没人理」，两者对处置的差别远小于「停在哪一段」。
6. **`last_error` 持久到下一次尝试**：登录尝试被受理时清空、转就绪时清空；进入未登录（登出）**不清空**——保留最近一次失败供回看（与 md 现有实现一致），进程重启后为空。
7. **连接超时（前置未连上）不加失败态**：它发生在登录链第一段之前，没有「失败阶段」可停，仍回 `min`，只写 `last_error` + 通知（理由见下 (B)）。这是决策 3 的第二类回退，不是链内失败。

**为什么不用其他方案**：

- **(A) 维持现状（回退 + 只补通知）**：只解决「弹窗一闪而过」的一半——失败后 `state` 仍是前一段的正常态，继续说谎；且回退把「会话尝试结束」与「失败」压成同一个信号，前端必须再找旁路才能区分「用户按了登出」与「登录失败了」。诊断成本从「看状态」退化成「拼两条互不对应的线索」，正是 #407 / #488 反复出问题的根因。
- **(B) 给连接超时也加失败态**：`min`（未登录）是唯一允许直接发起登录的端点，也是 `ACCOUNT_STATUS` 三态里 Offline 的成员；给它一个失败态会把「从未连上」报成「登录中」，改变策略侧看到的账户三态语义，并让「能否登录」的判定多一个特例。连接超时只补 `last_error` + 通知，位置仍是未登录。
- **(C) 只加 `last_error` 不加失败态**：`last_error` 只回答「原因」，回答不了「进度条为什么倒退回正常段」——`state` 继续说谎、用户看到的仍是「已登录」；且回退信号仍然是 pending 的唯一判据，失败与用户主动登出仍不可区分。位置（失败态）与原因（`last_error`）必须同时在场。
- **(D) 失败态复用单一 `Failed`**：单态只能回答「失败了」，回答不了「停在哪」——`current` 要么取一个固定值（丢掉进度位置，等价于把整条链压成一个态），要么维持回退（回到 (A) 的问题）。多段链上「哪一段」正是处置依据：认证失败要改授权码、登录失败要改密码、结算确认失败先看柜台、合约加载失败看网络与查询流控。反过来，单段链（md）本来就只需要一个失败态——「不复用单态」不等于「每个接口类型都必须多态」。
- **(E) 用 `min` / `max` 表达失败**：端点是「能不能发起登录 / 能不能用」的判据——`min` = 可登录、`max` = 就绪可用。把失败塞进任一端点，消费方就会把「失败」读成「可以再登录」或「已经可用」，正是本 ADR 要消除的说谎；端点语义跨接口类型固定（ADR 0051 决策 3 保留部分），不能为表达失败而重定义。`desc` 同理：只展示、不承载状态判定。

## Consequences

**正面**：失败后 `state` 与进度停在真实位置，用户与前端能回答「停在哪一段、为什么」；`current` 回退恢复单一含义（会话尝试就此结束），链内失败不再借用回退信号；`last_error` 让失败原因可持久回看，并给 pending 一个一致、可测的清除判据；通用规则只在骨架写一次，新增接口类型照抄，数值各自演进而骨架不漂移。

**负面 / 已知限制**：

- 失败态数量随接口类型的链长增长（td 四个、md 一个），前端状态文案与穷举需要逐个补齐——这是有意破坏：新增枚举值让 `Record<TdState, string>` 这类穷举在编译期失败，正是防漏保护。
- 前端必须同时消费进度与 `last_error` 两个来源，只看进度不再能判定失败；兜底超时仍要保留（`last_error` 缺失时是最后一道信号）。
- **回退信号不再等于「失败」，但也不等于「非失败」**：链内失败停住不回退，连接超时仍回 `min`。想把「这次尝试为什么结束」说清楚，唯一可靠的读法是状态帧的 `last_error`；只看回退只能得到「结束了」。
- **仍依赖「`current` 变化」判定的旧消费方在失败路径上会一直等到兜底超时**——失败停住后 `current` 不变，各接口类型契约必须显式改写该判据（本 ADR 只立规则，接线在实现票）。
- `0 < current < max` 这一段同时容纳「建立中 / 重连中 / 失败态」，单看数值无法区分三者；区分必须读状态帧（`state` / `last_error`）。进度数值从「能反推一切正常」退化为「只回答位置」。

**契约 / 文档同步**：《帧契约：进度推送》会话骨架改写；各接口类型状态与连接契约的数值 / 字段 / 码表 / 前端义务由 #493（通知出口收敛）+ #494–#497 承接；`GLOSSARY` 新增「登录失败态」，与该词条的「网关会话」「登出」词条互引。

**过渡期已知不一致（本 ADR 合入到 #494–#497 落地之间）**：下列文本仍按旧口径写「失败回退 / 失败态与正常阶段同值」，引用的是本 ADR 已删除的骨架条款——实现票必须逐个改写，否则仓库在过渡期自相矛盾：

- 《帧契约：交易账户连接控制》「前端义务」① 的「其余 = 建立中（连接中/登录中/重连中/失败回滚）」与 ② 的「`current` 相对上次推送回退（进度骨架：失败/中止会回退）」；
- 《帧契约：行情网关状态》失败语义的「失败态数值映射不变（与 `Connected` 同为 `current=2`）」与前端义务①的「回退…同样是清除信号」；
- `docs/components/dztd_ctp.md` 与《帧契约：交易账户连接控制》里的「失败回滚」措辞。

本 ADR 不改它们：通用规则先行、实现随票落地，这些是本 ADR 的下游。

## Supersedes

精确到句；未列出的决策与句子全部保留。

- [ADR 0051](0051-gateway-session-control-vocabulary-and-ui.md) 决策 3 中的「**失败不是端点**（md 登录失败态与已连接同为中间值）」——**整句废止**。失败仍不占端点（本 ADR 决策 1 继承这半边），但括号内的数值口径（失败态与正常阶段同值、靠回退表达）不再成立：失败停在失败阶段，`current` 取该段数值，由失败态本身表达「在哪失败」。
- [ADR 0051](0051-gateway-session-control-vocabulary-and-ui.md) Consequences 中「登录 pending 的失败清除依赖「`current` 回退」判据（进度骨架声明建立期单调、**失败回退**）」——**整句废止**，即「失败回退」这半边（票面记为「失败回滚会使 `current` 回退」）不再成立：链内失败不再使 `current` 回退，清除信号改为状态帧 `last_error` 的新时间戳；`current` 回退收窄为决策 3 列出的两类「会话尝试就此结束」。该句引用的骨架条款（「会话建立期的 `current` 单调不减；失败回滚或主动中止会使 `current` 回退」）由本 ADR 直接改写——契约不是 ADR，不走 Supersedes，改写结果见《帧契约：进度推送》。

**ADR 0051 继续有效的部分**：决策 1（命名分两层：动作 = 登录 / 登出、传输阶段 = 连接 / 断开）、决策 2（UI = 双按钮：登录仅 `current <= min` 可用、登出在 `current > min` 任意状态可用；其状态枚举里的「失败回滚」一词按本 ADR 改称「失败态」，规则本身不变）、决策 3 的其余内容（`min` 恒为未登录的唯一起点、`current == max` 为就绪、中间值由接口类型定义、消费方只按端点相对判定且禁止依赖具体数值）、决策 4（恢复统一两段式：失败 / 卡死一律先登出再登录，含「前端不提供失败态原地重试」）、决策 5（td 控制链路镜像 md），以及 Consequences 中除上面被废止那句外的表述。
