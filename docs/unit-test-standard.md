# 单元测试判据

> **用途**：判定「单元测试是否合格」的**唯一判据来源**。两种场合用它：
> 1. **撰写**——新增或修改测试时逐条对照；
> 2. **审查**——全仓测试审查（及后续复查）按条目编号出结论，发现引用形如 `§1.3`。
>
> **分工**：本文管「写得好不好」。**机制**（每文件一 target、`gtest_discover_tests`、`DZTRADER_HOME` 豁免、ctest 命名）在
> [build-appendix.md](agents/build-appendix.md) 的「单元测试约定」节；**位置与去向**在仓库根 `CONTRIBUTING.md` §4；
> **门禁动作**（每次 push 跑什么）在 [development-checklist.md](development-checklist.md) C 段。
> 本文不改它们的内容，只做判据。

## 判定词表

| 判定 | 含义 | 处置 |
|------|------|------|
| **失效** | 用例不成立（断言恒真、断言与承诺无关、测的不是被测对象），或长期禁用挂着 | 必须改 |
| **弱** | 能测到东西但强度不足（只测成功路径、断言过宽、只求不抛异常） | 建议改 |
| **缺失** | 契约或公开面上应有的用例不存在 | 建议补 |
| **合格** | 无发现 | — |

审查时每条发现写「维度编号 + 判定词」，例如 `§1.2 弱`。

## 适用范围

- C++：`libs/*/tests`、`apps/*/tests`、`strategies/demo/tests`（全量逐文件，不抽样）
- 前端：`apps/webui/frontend/src/**/__tests__`（见 §3.7）
- 覆盖基准：有契约的模块以 `docs/frame_contracts/` 为准（每帧、每字段组至少一个用例）；无契约的库以「公开 API 的错误路径与边界」为准

## 1. 有效性

| # | 判据 | 不合格长什么样 |
|---|------|----------------|
| 1.1 | **断言能失败**：每个用例至少一条断言，且被测实现被改坏时该断言必须变红 | 无断言；`ASSERT_NO_THROW` 单独成例；永真条件（`EXPECT_TRUE(true)`、`EXPECT_GE(x, 0)`、断言自己刚构造的对象）；只测「不崩溃」 |
| 1.2 | **断言对外承诺**：断言对象与被测单元的对外承诺同级——契约帧内容、返回值、错误码、状态转移、可观察副作用 | 断言私有成员或内部中间量（实现一重构测试就红）；只断言替身被调用次数而不看效果 |
| 1.3 | **契约锚定**：帧号、字段名、枚举值、必填与互斥语义与 `docs/frame_contracts/` 一致；契约语义被改坏时用例必须变红 | 期望值与契约漂移；只测成功路径字段；契约明示的校验/互斥无对应用例 |
| 1.4 | **错误路径与边界**：每个公开 API 与契约帧覆盖非法输入、越界/超长、错误码路径、空值与零值（呼应 [development-checklist.md](development-checklist.md) D3） | 只有成功路径 |
| 1.5 | **隔离与确定性**：不依赖执行顺序、不依赖墙钟时间、不依赖跨用例残留状态；同步用条件等待 | 同一二进制内顺序依赖；固定名临时目录跨运行残留；用 `sleep_for` 当同步手段 |
| 1.6 | **门控不掩盖缺陷**：`GTEST_SKIP` 与 `#ifdef` 只用于「环境不满足」（未配置 mysql、平台差异），不用于「功能未实现」 | 用 Skip 代替失败；平台分支里整段逻辑没有等价断言 |
| 1.7 | **禁用即处置**：`DISABLED_` 要么删除、要么降级为显式的可选慢速项、要么改成抽样版 | 长期 DISABLED 挂着；注释掉整段用例 |

## 2. 覆盖

| # | 判据 | 不合格长什么样 |
|---|------|----------------|
| 2.1 | **基准对齐**：有契约的模块，契约的每个帧/字段组至少一个用例；无契约的库，公开 API 的每条错误路径至少一个用例 | 契约里定义了但全仓无引用、无测试的帧或字段组 |
| 2.2 | **分支对等**：被测单元的主要分支（成功/失败/空输入/边界）都有用例 | 整个文件只测成功路径；异常分支从无用例 |
| 2.3 | **缺口判定不工具化**：本仓不引入覆盖率工具（`CONTRIBUTING.md` §4 明文：不设覆盖率指标），缺口靠人工对照契约与公开面判定 | — （此条是「明确不做」，见下） |

## 3. 一致性

| # | 判据 | 不合格长什么样 |
|---|------|----------------|
| 3.1 | **命名与位置**：`<主题>_test.cpp` 放被测模块的 `tests/`；前端 `src/**/__tests__/*.spec.ts` | 另起命名/另起目录 |
| 3.2 | **fixture 正确性**：共享 setup/teardown 用 `TEST_F`；fixture 不携带用例间可变状态 | fixture 里留残留状态；用例靠前一个用例的副作用 |
| 3.3 | **替身策略**：不引入 GMock（本仓零使用）；替身走注入回调或手写 fake，且 fake 必须可校验（记录调用与参数） | 只求「不炸就行」的空壳 stub；断言 fake 被调用次数而不看效果 |
| 3.4 | **`DZTRADER_HOME` 纪律**：遵循 AGENTS.md 硬门禁 2；自管临时目录的用例在 `SetUp` 设置、`TearDown` 恢复并清理；注意进程级缓存（`paths::configs()`）与单例的陷阱 | 依赖系统级环境变量；改环境变量后不恢复，污染同二进制其他用例 |
| 3.5 | **临时资源唯一化**：优先 `pid`/`uid`/随机后缀，避免固定名；用完清理；不写 `DZTRADER_HOME` 与系统临时目录以外的路径。直接用 `libs/core/tests/test_temp_dir.h` 的 `dztrader::test::unique_temp_dir()` / `unique_temp_path()`（进程唯一，进程内恒等——`paths::home()` 等按进程缓存，需同一用例内多次取到同一路径）。`gtest_discover_tests` 下每个用例是独立进程，`ctest -j` 并发时固定名目录会互踩（#136 实测 `DbConfigTest` 偶发失败）；新增固定名会被 preflight 的 `check_test_portability.py` 拦下 | 固定名目录（`temp_directory_path()/dz_xxx`）跨运行残留或在 `ctest -j` 下互删；手写唯一化重复基建而不复用共享头 |
| 3.6 | **日志断言合规**：断言日志文本时与 `scripts/check_log_format.py` 的规则一致（小写开头、无句号、`prose \| k=v`） | 断言了不合规的日志文本，等于把错误格式钉死 |
| 3.7 | **前端专段**：`vi.mock` 不得掩盖真实交互（mock 的是边界而非被测对象）；store 断言看状态迁移与副作用；不测真实布局（jsdom 局限），不依赖时间/随机 | mock 掉被测对象本身，测试变成同义反复 |
| 3.8 | **跨平台测试**：绝对路径用 `std::filesystem::temp_directory_path()` / `std::filesystem::absolute()` 构造，不写死 `/home/`、`/Users/`、`/root/`；定时器/调度测试的收集器必须过滤自身 guard timer id；时间断言用下界/条件等待，不依赖 Windows 计时粒度 | Linux 绿但 Windows 红；guard 帧被当作被测帧；绝对路径被解析到当前盘符 |

## 4. 成本

| # | 判据 | 不合格长什么样 |
|---|------|----------------|
| 4.1 | **耗时与价值匹配**：>1s 的用例须能说明价值（真并发/真进程/真 IO）；能用条件等待的不用 `sleep` | 为「等一会儿」而 sleep；纯计算用例跑成秒级 |
| 4.2 | **串行化与超时有据**：`RUN_SERIAL` / `TIMEOUT` 的使用须有理由（现状：135 例因共享 SHM 通道名，属正当） | 无条件 `RUN_SERIAL` 拖长全量时间；无 `TIMEOUT` 的挂死风险项 |
| 4.3 | **门禁可分层**：单测门禁内不混入无阈值的基准项（如 `PerfBench`）与可选的分钟级穷举项 | 基准项/穷举项与秒级单测同列，导致无法按「快/慢/集成」筛选 |

## 5. 基建（横切项，按系统判而非按用例判）

| # | 判据 | 不合格长什么样 |
|---|------|----------------|
| 5.1 | **注册方式唯一**：沿用每文件一 target + `gtest_discover_tests`；注意无 `TEST_PREFIX`，`-R` 只能按 `Suite.Case` 过滤 | 引入第二种注册/构建方式 |
| 5.2 | **重复基建需有据**：重复的 `test_main.cpp`、多份「同款 fixture」要么注明理由（先例：build-appendix 已写明「部分模块有意只编译源码子集」），要么收敛 | 纯复制粘贴且无人能说出为什么 |
| 5.3 | **产物去向有意**：测试二进制的 install 行为应是有意决定 | 无人知道为何被安装 |

## 明确不做

- 不引入覆盖率工具（`CONTRIBUTING.md` §4；行覆盖 ≠ 行为覆盖）
- 不引入 GMock（替身走注入回调 / 手写 fake）
- 审查期不改代码：审查产出发现，修复走后续波次
- 不审冒烟测试的**业务正确性**（`apps/master/tests/smoke/` 按「测试质量」审，不按业务语义审）
- `apps/ctp/md/` 生产锁定：只读纳入审查，任何改动须先确认（AGENTS.md 硬门禁 1）

## 生效范围与维护

- **新写的测试强制适用**；存量测试按 §3.5 等条目的整改范围以审查结论为准（一次性整改 vs 存量豁免由审查决策）
- 判据变更直接改本文；与 build-appendix / CONTRIBUTING 的重叠按「本文管判据，彼处管机制与位置」消解
